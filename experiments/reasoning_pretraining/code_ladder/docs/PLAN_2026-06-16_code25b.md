## Lessons baked in (from 2026-06-15 audit)

These are the "shard and data size issues you faced yesterday" that Dongwei asked me to keep in mind:

1. **Token-proportional ≠ uniform-per-shard**. The original SP-NL setup weighted 228 part-dirs uniformly, giving chunk1's 128 small parts 56% of the SP-NL weight share for only 19.8% of the rows. Always weight by `rows / total_rows`.
2. **MixtureDataset rounding bug**. Default `_compute_expected_counts_per_block` truncated weights × block_size to int and dumped the entire remainder into the argmax floor. With 228 small components, that gave SP-NL 81% / code 17% / markup 2% instead of intended 90/8/2. Fixed in `lib/levanter/.../mixture.py` with Hamilton/largest-remainder apportionment. **This code25b run uses only 6 components — Hamilton drift is bounded by 1 sample per block; safe.**
3. **`_resolve_cache` strict-single-match**. No `matches[-1]` silent-pick when a retokenize creates a second hash. The new script raises if `len(matches) > 1`.
4. **DatasetComponent.offset slices SHUFFLED-position**, not raw-cache space. Not relevant here (single-phase, no offset). But documented in `lib/levanter/.../data/text/datasets.py` regression test.
5. **Levanter shuffle keys come from `key_iter` in dict-iteration order**. For multi-phase replay (C5-v6-NEW), components must be in the SAME insertion positions across phases. Not relevant here (single-phase). But also documented.
6. **`log_jaxprs=False, log_xla_hlo=False`** is now the TrainerConfig default in `lib/levanter/.../trainer.py`. Bypasses the wandb-core nil-ctx panic + md5 SIGBUS. Means online wandb should "just work" for this launch on attempt 1 — no retry chain needed in theory. But the orchestrator does keep a 5-attempt retry loop in case some other wandb code path triggers a different bug.
